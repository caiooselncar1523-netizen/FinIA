# ADR-0001: Escolha do stack de frontend e backend

**Status:** Aceito
**Data:** 2026-09-17

## Contexto

O FinIA precisa de uma interface responsiva com gráficos e dashboards (frontend) e uma API que lide com autenticação, regras de negócio financeiras e integração com APIs externas (backend). O projeto também tem um objetivo secundário importante: servir de peça de portfólio para demonstrar domínio de arquitetura full-stack.

## Decisão

- **Frontend:** Next.js + TypeScript + Tailwind CSS + Recharts.
- **Backend:** Node.js com NestJS (ou FastAPI em Python como alternativa equivalente).
- **Plataforma:** Web app responsivo (PWA), não app nativo nesta fase.

## Alternativas consideradas

- **App nativo (React Native) desde o início** — descartado por aumentar a complexidade de manutenção (dois códigos ou um bridge) sem necessidade no MVP. PWA cobre boa parte da experiência mobile.
- **Backend em Django/Ruby on Rails** — frameworks maduros e produtivos, mas o ecossistema Node/TypeScript unifica a linguagem entre frontend e backend, reduzindo troca de contexto.
- **Frontend em Vue/Nuxt** — igualmente viável, mas Next.js tem ecossistema maior de bibliotecas de gráficos e é mais comum em vagas de mercado, o que pesa no objetivo de portfólio.

## Consequências

- Um único idioma (TypeScript) do banco até a interface facilita manutenção solo.
- Next.js permite migrar facilmente para app nativo depois via React Native, reaproveitando lógica.
- Se o projeto crescer muito em volume de dados/processamento pesado de IA, pode valer reavaliar um serviço em Python só para essa camada (ver ADR futuro se isso ocorrer).
- **Decisão explícita (2026-09-17):** avaliamos usar Python desde já por conta de bibliotecas de ML/dados, mas decidimos adiar. No MVP, o uso de IA é limitado a orquestração de LLM (chamadas à API da Claude), o que TypeScript resolve sem perda de capacidade. Python só entraria como microsserviço isolado se, no futuro, o produto precisar de machine learning treinado (não apenas chamadas a LLM via API).
